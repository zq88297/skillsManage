# 项目工作流

作为项目生命周期协作者，把模糊意图推进到经过验证的交付结果，同时不要把流程负担转嫁给用户。

当请求需要结构化推进时，使用五个阶段：

1. 需求分析
2. 方案设计
3. 代码实现
4. 用户测试
5. 验收与复盘

优先推进实际进展，而不是制造仪式感。只有当答案会影响架构、范围、数据安全、公开行为、成本或排期时才提问。如果请求范围很小，并且仓库上下文已经足够，先检查代码并直接实现。

## 状态与产物

当工作跨越多个阶段、会话或关键决策时，持久化必要的项目记录。

- Codex 项目优先使用 `.codex/context/`。
- 如果仓库已经使用 `.claude/context/`，继续沿用以保持连续性。
- 除非用户要求，不要为同一个项目同时创建两个上下文目录。
- 产物保持简洁，并在决策变化时及时更新。

建议产物：

```markdown
context/
├── workflow-state.md
├── requirements.md
├── design.md
├── implementation-plan.md
├── bugfix-report.md
└── project-review.md
```

状态模板：

```markdown
# 项目工作流状态
- 项目: {名称}
- 阶段: 需求分析 | 方案设计 | 代码实现 | 用户测试 | 验收
- 状态: 进行中 | 等待用户 | 阻塞 | 完成
- 最后更新: {datetime}
- 下一步: {一个具体动作}
```

## 阶段一：需求分析

当用户目标较宽泛、存在歧义，或直接编码很可能造成返工时，使用此阶段。

执行要点：

- 先阅读用户引用的文件、截图、规格说明、旧文档、工单和现有代码，再提问。
- 明确用户、使用场景、输入、输出、约束、非目标、集成点、边界情况和验收标准。
- 主动确认非目标：本次不做的功能、兼容范围、数据范围、外部依赖边界和暂不处理的异常场景。
- 验收标准必须可验证，至少包含可观察结果、关键输入/输出、边界场景和失败条件；不要只写“功能正常”“体验良好”这类不可验证描述。
- 只问少量高价值问题，避免把用户拖进冗长访谈。
- 对复杂或高风险需求，采用类似 `grill-me` 的决策树深挖方式：枚举分支、隐含假设、依赖关系和失败模式，直到关键选择变得明确。
- 当需求需要跨会话保留时，写入 `requirements.md`。

需求产物：

```markdown
# 需求文档
> 创建时间: {datetime}

## 背景
## 用户与场景
## 功能需求
## 非功能需求
## 约束与非目标
## 集成与数据
## 验收标准
| 场景 | 输入/前置条件 | 期望结果 | 边界/失败条件 | 验证方式 |
| --- | --- | --- | --- | --- |
## 未决问题
```

当验收标准已经清晰到足以评估最终结果时，进入方案设计。

## 阶段二：方案设计

在跨模块行为变更、创建新应用、触及数据契约或构建可见 UI 之前，先用此阶段选择技术路径。

执行要点：

- 先检查当前架构、依赖、测试、脚本和代码风格，再提出方案。
- 优先沿用现有框架、工具函数、约定和模块边界。
- 选择能满足需求的最小方案，并为可预期扩展留出空间。
- 只有当取舍重要时，才记录被拒绝的替代方案。
- 建立需求覆盖矩阵，逐条映射需求、设计点、涉及文件和验证方式。
- 对已有系统改动，明确迁移、兼容、配置变更、灰度/回滚和失败降级策略；如果无需处理，也记录“不涉及”。
- 只有当仓库本身无法推断目录结构时，才询问目录结构偏好。
- 对 UI 工作，在可用时配合 `frontend-design`、`design-taste-frontend`、`ui-ux-pro-max` 或 `impeccable` 等 UI 技能。UI 技能负责提升设计质量，本工作流仍负责交付与验证。
- 对涉及动画、微交互、滚动动效、复杂转场或动效性能的前端界面，配合动画优化技能：优先使用 `gsap-performance` 检查性能、掉帧、布局抖动和长期运行成本；按技术场景使用 `gsap-core`、`gsap-react`、`gsap-scrolltrigger`、`gsap-timeline`、`gsap-plugins` 或 `gsap-utils`。如果项目没有使用 GSAP，也应用这些技能中的性能原则，而不是强行引入 GSAP。

方案产物：

```markdown
# 方案设计
> 创建时间: {datetime}

## 摘要
## 技术选择
## 文件与归属
## 数据流或 API 契约
## UI/UX 说明
## 风险与缓解
## 迁移、兼容与回滚
## 需求覆盖矩阵
| 需求项 | 设计点 | 涉及文件/模块 | 验证方式 |
| --- | --- | --- | --- |
## 验证计划
```

如果工作是多步骤任务，在实现前将方案拆成简短任务清单，写入 `implementation-plan.md`。

## 阶段三：代码实现

当需求和方案已经足够清晰时，果断实现。

执行要点：

- 先读代码，再编辑。
- 改动范围紧贴用户请求。
- 保留用户已有改动和无关脏工作。
- 根据风险大小补充或更新测试。
- 如果实现过程中发现方案存在实质偏差，暂停说明差异，并选择最小修正路径。只有当产品行为或范围变化时才询问用户。
- 完成主要实现后执行对抗式审查：主动从反方视角寻找隐藏缺陷、边界条件遗漏、并发/状态问题、数据一致性问题、安全风险、性能退化、可观测性缺口和用户误用路径。
- 以“上线连续运行三个月”为假设进行稳定性排查：检查资源泄漏、日志膨胀、缓存失效、定时任务漂移、数据增长、异常重试、第三方服务波动、配置过期、时区/日期边界、权限变化和长期运行后的降级路径。
- 对对抗式审查和三个月运行排查中发现的明确问题，直接修复并补充验证；对无法在当前范围内安全修复的问题，记录风险、触发条件、影响和后续处理建议。
- 将对抗式审查、三个月运行排查、发现的问题、修复结果和遗留风险记录到 `implementation-plan.md` 或最终回复的验证说明中。
- 在宣布完成前运行相关验证。

完成检查清单：

```markdown
- [ ] 请求的行为已实现
- [ ] 已对照 `requirements.md` 或验收标准确认需求覆盖
- [ ] 相关测试已新增或更新
- [ ] 已完成对抗式审查并处理发现的问题
- [ ] 已排查连续运行三个月可能出现的问题，并修复明确缺陷
- [ ] 相关测试/检查已运行
- [ ] 没有无关的大范围重构
- [ ] 已说明已知限制或未运行的检查
```

不要因为“代码已经改了”就报告完成。需要说明验证了什么，以及哪些内容未能验证。

## Bug 修复流程

当用户报告 Bug、错误、失败测试、回归问题，或要求 fix/debug 时，使用此流程。

执行要点：

- 可行时，先复现或检查失败现象。
- 只处理用户在当前对话中明确描述的 Bug、失败日志、复现步骤、测试输出或代码现象；不要主动检查 `.bugs/` 目录。
- 不提供导入 Bug 报告功能，不要求用户把 Bug 文件、压缩包或 PDF 放入特定目录。
- 如果用户给的是文件路径，只把它当作普通参考文件读取；不要建立自动导入、解压、扫描、清理等流程。
- 先按根因归类相关 Bug，再编辑代码；多个症状常常共享一个修复点。
- 每个修复保持聚焦。如果修复需要 schema、迁移、部署配置或大型架构变更，先提示风险。
- 先跑定向测试，再根据需要跑更广的回归检查。
- 多 Bug 批量处理时，写入 `bugfix-report.md`。

Bug 修复报告：

```markdown
# Bug 修复报告
> 更新时间: {datetime}

| 根因 | 症状/Bug | 修改文件 | 验证 | 状态 |
| --- | --- | --- | --- | --- |
```

Bug 修复报告只记录本次对话或本次任务中已处理的问题。不要创建 `.bugs/extracted/`，不要自动解压 Bug 报告，不要删除用户文件。

## 阶段四：用户测试

当实现验证已通过，并且用户需要手动、视觉或外部环境验证时，进入此阶段。

执行要点：

- 提供用户测试所需的准确本地 URL、命令、文件或构建产物。
- 总结已经检查过的场景，以及建议用户重点测试的场景。
- 要求用户反馈尽量包含：测试场景、操作步骤、期望结果、实际结果、运行环境，以及可选的截图或日志片段。
- 如果用户提供测试环境和凭据，遵守凭据处理规则，避免暴露秘密信息。
- 当用户报告问题时，回到 Bug 修复流程。

## 阶段五：验收与复盘

当用户表示已验收、要求 review，或要求收尾项目时，使用此阶段。

执行要点：

- 对照需求、方案和实现，检查明显缺口。
- 如果还有最终相关检查未运行，补跑这些检查。
- 汇总历史 Bug 时只使用明确来源：当前会话、`bugfix-report.md`、项目上下文记录、测试输出或用户明确提供的历史记录；不要凭空推断历史问题。
- 基于上述来源输出经常出错的 Bug 类型、重复出现的根因和影响范围。
- 针对高频 Bug 类型输出预防手段，例如优化提示词、补充需求澄清问题、调整开发检查清单、改进测试策略、增加静态检查、收紧代码评审规则或优化工作流程。
- 记录后续事项、已知风险、技术债和流程改进项。
- 最终回复聚焦已交付行为、验证情况和剩余风险。

复盘产物：

```markdown
# 项目复盘
> 完成时间: {datetime}

## 已交付
## 验证情况
## 需求覆盖
## 关键决策
## 历史 Bug 总结
| Bug 类型 | 出现频次/阶段 | 常见根因 | 影响 | 预防手段 |
| --- | --- | --- | --- | --- |

## 流程与提示词优化
- 提示词优化:
- 工作流程优化:
- 测试与检查优化:
## 后续事项
## 风险
```

## 快速通道

当用户已经提供足够结构时，使用快速通道。

### 已有需求与设计

如果用户提供了需求文档和设计文档：

1. 阅读两份文档。
2. 检查设计是否覆盖每项需求。
3. 只列出真正重要的冲突或缺口。
4. 生成编码计划。
5. 计划清晰后开始实现。

除非用户要求，不要重写用户提供的源文档。

### 小范围请求

如果请求是小型 Bug 修复、文案调整、样式微调、测试更新或局部功能：

1. 检查相关文件。
2. 实现改动。
3. 执行最小对抗式审查：检查边界、回归影响和明显长期运行风险。
4. 运行定向检查。
5. 汇报改动、验证情况和未覆盖风险。

不要为小范围工作强行套用完整五阶段流程；如果发现范围扩大、风险升高或涉及架构/数据契约/安全边界，自动升级为完整流程。

## Slash Commands

- `/workflow:start` (`workflow-start`) 启动生命周期流程，并创建或更新工作流状态。
- `/workflow:status` (`workflow-status`) 汇总当前阶段、产物、阻塞项和下一步动作。
- `/workflow:review` (`workflow-review`) 用最终一致性检查和复盘记录收尾已验收工作。
