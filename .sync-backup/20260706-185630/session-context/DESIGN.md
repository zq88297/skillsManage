# Session Context Skill — 设计文档

> 本文档记录 `session-context` 技能的设计思路、架构模式和核心原则，
> 供 Codex 或其他 AI 在生成类似技能时参考。

---

## 1. 设计哲学

### 1.1 AI 自驱动，用户零操作

**核心原则：** 用户不应该需要记住任何命令或手动触发任何流程。所有上下文管理操作都由 AI 自动判断时机并执行。

**体现：**
- 对话开始时自动加载上下文（规则 0），不需要用户说 `/session-load`
- 检测到项目未初始化时直接执行初始化（规则 5），不只询问
- 对话中主动检测健康状态（规则 3），不等用户输入 `/context-check`
- 做出技术决策后主动提醒归档（规则 4）

**设计权衡：** 宁可多提醒一次（用户可以忽略），也不要让用户忘记保存而丢失上下文。

### 1.2 先理解后加载，不盲目读文件

**核心原则：** 不要先加载所有上下文再理解用户问题。先用 1 秒判断用户意图，再决定加载什么。

**体现：**
- 用户提到 bug → 先检查 `.bugs/` 目录（步骤 0），不先读 context 文件
- 复杂项目 → 先判断涉及哪个子模块，只加载相关上下文
- 简单项目 → 直接加载，不做多余判断

**设计权衡：** 加载速度 vs 完整性。宁可少读一点（后续可以补充），也不要让用户等 30 秒才开始回答。

### 1.3 任务记录是强制的

**核心原则：** 每次对话加载上下文后，**必须**将用户请求写入 `current-task.md`。这不是可选步骤。

**体现：**
- 规则 0 明确要求：加载后**立即**写入 current-task.md
- 写入是覆盖式（不是追加），保持文件精简
- 任务全完成时自动归档到 reference/，清空旧任务

**设计权衡：** 强制写入增加了少量 token 消耗，但保证了跨会话的任务连续性。

## 2. 架构模式

### 2.1 文件即状态

所有会话状态都存储在文件系统中，不依赖任何外部服务或数据库：

```
.claude/context/
├── current-task.md        ← 任务状态（覆盖更新）
├── decisions.md           ← 决策历史（追加更新）
├── pitfalls.md            ← 踩坑历史（追加更新）
├── architecture.md        ← 项目架构（context-sync 生成）
├── reference/             ← 永久技术参考（归档）
└── tasks/                 ← 跨项目任务（派发/接收）
```

**好处：**
- 零依赖，任何项目都能用
- 文件可 gitignore，不污染仓库
- 人类可直接阅读和编辑
- AI 用 Read/Write 工具即可操作

### 2.2 两种更新策略

| 文件 | 策略 | 原因 |
|------|------|------|
| `current-task.md` | **覆盖** | 只关心当前状态，不需要历史 |
| `decisions.md` | **追加** | 决策历史有参考价值 |
| `pitfalls.md` | **追加** | 踩坑记录需要累积 |
| `architecture.md` | **覆盖** | 只反映当前结构 |

**设计要点：** 覆盖式文件用 Write，追加式文件用 Edit（在末尾添加）。

### 2.3 分层上下文（大型项目）

```
项目根/
├── .claude/context/           ← 项目级
├── 子系统A/
│   ├── .claude/context/       ← 子系统级
│   └── 子模块A1/
│       └── .claude/context/   ← 模块级（任意深度）
└── 子系统B/
    └── .claude/context/       ← 子系统级
```

**核心规则：** 在哪层工作就读哪层的上下文，不向上/横向扫描。

**子模块识别标准：**
- ✅ 有独立构建配置（Makefile、CMakeLists.txt、package.json）
- ✅ 有 main 入口文件
- ❌ 排除通用目录（src/、lib/、tests/、node_modules/）

### 2.4 分支隔离

| VCS | 隔离方式 | 上下文路径 |
|-----|---------|-----------|
| SVN | 物理目录隔离 | `$(pwd)/.claude/context/` |
| Git | 子目录隔离 | `.claude/context/{branch-name}/` |

**Git 特殊处理：** 每次操作前 `git rev-parse --abbrev-ref HEAD` 获取分支名，自动切换上下文。

## 3. 核心规则设计

### 3.1 规则 0：智能加载（最高优先级）

```
用户提问
  │
  ├─ 步骤 0：bug 关键词？→ 检查 .bugs/
  ├─ 步骤 1：快速判断项目类型（ls 顶层目录）
  ├─ 简单项目？→ 直接加载 .claude/context/
  └─ 复杂项目？→ 定位子模块 → 检查分支 → 加载目标上下文
```

**设计思路：** 用最少的文件操作（1 次 ls）判断项目类型，然后走最短路径。

### 3.2 规则 3：健康自诊断

**不使用轮数作为指标。** 一轮轻量问答和一轮读取数万行代码，对上下文消耗天差地别。

**使用的信号：**

| 信号 | 严重度 | 说明 |
|------|-------|------|
| 系统注入了 conversation summary | 🟡 | 早期内容已被压缩 |
| 无法回忆起之前讨论的细节 | 🔴 | 关键信息丢失 |
| 回复质量明显下降 | 🟡 | 上下文接近饱和 |
| 重复读取已读文件 | 🟡 | 文件内容被挤出 |
| 用户纠正超过 2 次 | 🔴 | 上下文不完整 |

**设计思路：** AI 持续自监控，发现异常时主动汇报，不等用户发现。

### 3.3 规则 4.55：关键文件清单（跨会话接力）

当上下文即将耗尽时，在 `current-task.md` 中追加：

```markdown
## 📂 关键文件清单
### 问题定位相关
- src/ike/negotiate.c:240-350  ← SA 协商主逻辑
### 已排除的文件（不需要再看）
- src/ike/crypto.c            ← 已验证正常
### 当前排查结论
- SA 状态机在超时后未正确重置
```

**设计思路：** 新会话 30 秒内接续工作，不需要重新探索项目结构。

### 3.4 规则 4.7：跨项目任务派发

```
项目 A 排查中发现根因在项目 B
  │
  ├─ 在 B 的 .claude/context/tasks/ 创建任务文件
  ├─ 在 A 的 current-task.md 记录派发
  └─ B 开会话时 /session-load 优先展示外来任务
```

**设计思路：** A 和 B 各自维护各自的上下文，通过 tasks/ 目录通信。A 只写一次文件，不需要维护 B 的状态。

### 3.5 规则 6.5：文件瘦身

| 文件 | 读取策略 | 原因 |
|------|---------|------|
| `current-task.md` | 完整读取 | 覆盖更新，不会膨胀 |
| `decisions.md` | 只读最近 10 条 | 旧决策基本不会再查 |
| `pitfalls.md` | 只读最近 10 条 | 旧踩坑已内化为共识 |
| `architecture.md` | 完整读取 | 大小稳定 |

**归档条件：** 文件超过 200 行 或 条目超过 6 个月 → 移到 `*-archive.md`。

## 4. Skill 文件结构规范

### 4.1 目录结构

```
.claude/skills/{skill-name}/
├── SKILL.md              ← 技能主文件（规则 + 逻辑）
├── DESIGN.md             ← 设计文档（本文档类型）
└── commands/
    ├── command-1.md      ← 命令 1 的执行流程
    ├── command-2.md      ← 命令 2 的执行流程
    └── ...
```

### 4.2 SKILL.md 结构

```markdown
---
name: skill-name
description: "触发条件描述（越详细越好）"
---

# 技能标题

简短说明这个技能做什么。

---

## 核心概念

解释关键概念和术语。

---

## 自动规则（全局生效）

### 规则 N：规则名称

触发条件、执行流程、设计权衡。

---

## 命令参考

- `/command-1` → 简短描述
- `/command-2` → 简短描述
```

### 4.3 命令文件结构

```markdown
# 命令名称

简短说明这个命令做什么。

## Step 1: 第一步

具体操作步骤。

## Step 2: 第二步

具体操作步骤。

## Step N: 初始化（如果需要）

当目标不存在时的自动初始化流程。
```

### 4.4 description 字段规范

description 是技能的触发条件，越详细越好：

```markdown
description: "MUST trigger on EVERY conversation. Trigger on: 关键词1, 关键词2,
  /command-1, /command-2, 任何对话的第一句话."
```

**要点：**
- 列出所有触发关键词（中英文都要）
- 列出所有相关命令
- 说明触发优先级（如 "EVERY conversation"）

## 5. 关键设计模式

### 5.1 降级模式

当主要流程失败时，自动降级到更简单的方案：

```
尝试读取 .claude/context/ → 不存在
  │
  ├─ 尝试 docs/ai-context/ → 存在就用
  └─ 都不存在 → 自动初始化
```

### 5.2 确认 vs 直接执行

| 场景 | 行为 | 原因 |
|------|------|------|
| 初始化上下文 | 直接执行 | 用户不想被问"要不要初始化" |
| 归档旧记录 | 询问确认 | 归档不可逆，需要用户确认 |
| 安装 hooks | 询问确认 | 修改 .claude/ 目录需要确认 |
| 写入 current-task.md | 直接执行 | 强制步骤，不需要确认 |

**设计原则：** 低风险操作直接执行，高风险操作询问确认。

### 5.3 向后兼容

新版本的技能必须兼容旧版本的文件结构：

```
优先使用：.claude/context/
兼容旧版：docs/ai-context/
```

检测到旧路径时自动使用，不强制迁移。

### 5.4 幂等性

所有操作都是幂等的——重复执行不会产生副作用：

- 初始化：检查目录是否存在，存在就跳过
- 写入 current-task.md：覆盖式写入，不是追加
- 安装 hooks：检查文件是否存在，存在就跳过

## 6. Token 消耗优化

### 6.1 加载时优化

- `decisions.md` / `pitfalls.md` 只读最近 10 条
- 大文件用 `tail -50` 取末尾
- 简单项目不做子模块扫描

### 6.2 写入时优化

- current-task.md 覆盖式（不追加）
- 归档旧条目到 archive 文件
- 关键文件清单只记录路径和行号，不复制代码

### 6.3 提醒时优化

- 健康报告用精简格式（不阻塞对话）
- 只在异常时汇报，正常时不输出
- 归档提示用一句话，不展开说明

## 8. 反模式（避免）

### ❌ 盲目加载

不要先读所有文件再理解用户问题。先判断意图，再决定加载什么。

### ❌ 询问用户是否初始化

检测到未初始化时直接执行，不要问"要不要初始化"。

### ❌ 用轮数判断健康度

一轮读取 10 行代码和一轮读取 10000 行代码，对上下文的消耗完全不同。

### ❌ 追加式写入 current-task.md

current-task.md 应该覆盖式写入，只保留当前状态。追加会导致文件无限膨胀。

### ❌ 将敏感信息写入持久化文件

账号密码只写在 current-task.md（任务完成后删除），绝不写入 decisions.md、architecture.md。

### ❌ 跨模块扫描

在哪层工作就读哪层的上下文，不要向上或横向扫描其他模块。
